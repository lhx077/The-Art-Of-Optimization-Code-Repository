1. OBJECTIVE
================================================================================

This exercise focuses on identifying memory allocation hotspots in a real .NET
project using diagnostic tools. By the end of this exercise, you should be
able to:

  - Use Visual Studio Diagnostic Tools or dotnet-trace to capture allocation
    profiles from a running .NET application.
  - Identify the top 5 allocation hotspots by volume and type.
  - Propose optimization strategies for each hotspot.
  - Validate optimizations using BenchmarkDotNet with MemoryDiagnoser.

This is a tool-driven, open-ended exercise. There is no single correct output.
The goal is to develop proficiency with the allocation profiling workflow.

================================================================================
2. TOOL SETUP
================================================================================

2.1 Visual Studio Diagnostic Tools (Windows)
--------------------------------------------------------------------------------

  1. Open your .NET solution in Visual Studio 2022.
  2. Debug -> Performance Profiler (Alt+F2).
  3. Select ".NET Object Allocation Tracking" checkbox.
  4. Click "Start" to begin profiling.
  5. Exercise the application (run requests, process data, etc.).
  6. Stop the profiler and examine the "Allocations" tab.

The Allocations tab shows:
  - Total allocation count and size per type.
  - Allocation call stacks for each type.
  - Timeline of allocations correlated with GC events.

2.2 dotnet-trace with GC Allocation Events
--------------------------------------------------------------------------------

Installation:
  dotnet tool install --global dotnet-trace

Capture allocation tick events:
  dotnet-trace collect \
    --providers Microsoft-Windows-DotNETRuntime:0x200001:5 \
    -p <PID> \
    -o alloc_trace.nettrace

  Keywords: 0x200001 = GC (0x1) + GCAllocationTick (0x200000)
  GCAllocationTick fires approximately every 100 KB of allocation.

Open the trace in PerfView or Visual Studio for analysis.

2.3 BenchmarkDotNet with MemoryDiagnoser
--------------------------------------------------------------------------------

For validating optimizations, use BenchmarkDotNet:

  [MemoryDiagnoser]
  public class AllocationBenchmarks
  {
      [Benchmark(Baseline = true)]
      public void OriginalImplementation() { ... }

      [Benchmark]
      public void OptimizedImplementation() { ... }
  }

MemoryDiagnoser reports:
  - Allocated: total bytes allocated per operation.
  - Gen0/Gen1/Gen2: GC collections triggered per 1000 operations.

3. STEP-BY-STEP PROCEDURE
================================================================================

Step 1: Select a Target Application
--------------------------------------------------------------------------------
Choose a .NET application you are familiar with. It can be:
  - An ASP.NET Core web API
  - A console application that processes data
  - A background service or worker

The application should perform meaningful work (not just "Hello World").

Step 2: Capture an Allocation Profile
--------------------------------------------------------------------------------
Use one of the tools from Section 2 to capture allocations while the
application is under load. Aim for at least 30 seconds of profiling data.

For web APIs, use a load testing tool (bombardier, hey, k6) to generate
traffic during the profiling window.

Step 3: Identify the Top 5 Hotspots
--------------------------------------------------------------------------------
Sort allocations by total allocated bytes (not count). Record:

  Rank | Type Allocated        | Total Bytes | Count  | Top Call Stack
  -----|----------------------|-------------|--------|------------------
  1    | [e.g., System.String]| [X MB]      | [N]    | [Method chain]
  2    |                      |             |        |
  3    |                      |             |        |
  4    |                      |             |        |
  5    |                      |             |        |

Step 4: Propose Optimizations
--------------------------------------------------------------------------------
For each hotspot, propose at least one optimization:

  - String allocations -> StringBuilder, string.Create, Span<char>
  - byte[] allocations -> ArrayPool<byte>.Shared
  - List<T> / Dictionary<T> -> Pre-sized with known capacity
  - LINQ allocations -> Manual loops, struct enumerators
  - Boxing -> Generic methods, constrained calls
  - Closure allocations -> Static lambdas, cached delegates

Step 5: Implement and Validate
--------------------------------------------------------------------------------
Pick the top 1-2 hotspots and implement the optimization. Create a
BenchmarkDotNet benchmark comparing before and after. Verify that:

  1. Allocated bytes decreased (check the "Allocated" column).
  2. Gen 0 collections decreased or went to zero.
  3. Throughput did not regress (Mean time should be same or better).

5. COMMON HOTSPOT PATTERNS
================================================================================

5.1 String Concatenation in Loops
  Problem:  "result += item.ToString()" allocates a new string per iteration.
  Fix:      Use StringBuilder or string.Create with known length.

5.2 LINQ Chains Creating Iterator Objects
  Problem:  .Where().Select().ToList() creates 3+ iterator objects + final list.
  Fix:      Single foreach loop with manual filtering and pre-sized list.

5.3 params Array Allocations
  Problem:  Methods with params T[] allocate a new array per call.
  Fix:      Provide overloads for common arities (1, 2, 3 args).

5.4 Temporary Collections
  Problem:  Creating List<T> or Dictionary<K,V> for short-lived intermediate
            results.
  Fix:      Use ArrayPool, stackalloc, or restructure to avoid the
            intermediate collection.

5.5 Boxing in Generic Constraints
  Problem:  Passing structs to methods accepting object or non-generic
            interfaces.
  Fix:      Use generic methods with struct constraints to avoid boxing.
