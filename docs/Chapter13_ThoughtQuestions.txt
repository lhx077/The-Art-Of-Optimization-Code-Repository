Chapter 13 — The Inner Workings of the JIT Compiler
              Thought Question Answers

Question 1: Why is method inlining considered the most important JIT
optimization? Beyond eliminating call overhead, what indirect optimization
opportunities does inlining enable?
--------------------------------------------------------------------------------

Inlining matters because removing the call instruction is only part of the gain.
The bigger payoff is that once the callee body is merged into the caller, the
optimizer can see through the boundary and perform additional simplifications.

Without inlining, the optimizer must respect the call boundary. It often cannot
propagate constants, fold conditions, remove redundant loads, or combine logic
across that boundary because the callee is treated as a separate unit.

With inlining, several improvements become possible:

  - the direct call overhead disappears
  - constant arguments can be substituted into the former callee body
  - dead branches inside the callee may vanish
  - local values may stay in registers more effectively
  - surrounding expressions can be simplified as one larger region

For example, a tiny helper like:

  static int ClampToZero(int x) => x < 0 ? 0 : x;

seems cheap already. But if it is inlined into a caller where x is already known
to be non-negative, the entire operation may disappear.

Inlining is therefore important not because calls are always expensive by
themselves, but because call boundaries can block whole chains of optimization.
The JIT must still be selective, though. Over-inlining can increase code size,
hurt instruction cache locality, and slow compilation.


Question 2: How does the JIT perform bounds-check elimination? Why is the
standard for loop pattern easy to optimize, while certain variants are not?
--------------------------------------------------------------------------------

The JIT can remove bounds checks when it proves that every index used by the
loop stays within the valid range of the array. Bounds checks are inserted for
safety, but if they are provably redundant, removing them reduces branches and
instruction count.

To do that safely, the JIT needs facts such as:

  1. The loop variable starts in a valid range.
  2. The loop exit condition guarantees the variable never reaches an invalid
     index.
  3. The indexed array reference inside the loop is the same array whose length
     participates in the guard.
  4. No arithmetic transformation inside the index expression can overflow or
     produce a value outside the proven range.

A classic example is:

  for (int i = 0; i < array.Length; i++)
      sum += array[i];

Here the runtime can often infer that i is always between 0 and array.Length-1,
so a separate range check on each iteration becomes unnecessary.

However, if the loop is written in a more complex way, such as indexing through
multiple offsets or mixing unrelated lengths, the proof becomes harder. The JIT
is not trying to be mathematically omniscient; it uses practical analyses that
must stay fast enough for runtime compilation.

So bounds-check elimination is fundamentally a proof problem. The JIT removes
checks only when it can prove safety, not merely suspect it.


Question 3: How does tiered compilation balance startup time and steady-state
performance? In what scenarios might you want to disable it?
--------------------------------------------------------------------------------

Tiered compilation means the runtime does not commit immediately to one final
code generation strategy for every method. Instead, it may first generate a
cheaper, quicker-to-produce version of a method and later replace it with a more
optimized version if the method proves hot.

This improves overall runtime behavior because not every method deserves maximum
optimization effort. Many methods run only a few times. Spending expensive JIT
analysis on all of them would hurt startup for little benefit.

The usual idea is:

  - Tier 0: fast compilation, modest optimization, good startup
  - Tier 1: slower compilation, stronger optimization, better steady-state speed

A method's performance can therefore change over time because the first calls may
execute Tier 0 code, while later calls run Tier 1 code after the runtime decides
that the method is important enough to optimize further.

You might want to disable tiered compilation in certain scenarios:

  1. Latency-critical services where even early requests must meet strict SLAs
     and you cannot afford Tier 0 code running in the hot path.
  2. Microbenchmarking where you want to measure only steady-state performance
     and tiered warmup introduces noise (though BenchmarkDotNet handles this).
  3. Debugging JIT behavior when you want to inspect only the fully-optimized
     Tier 1 output without interference from Tier 0 code.
  4. Deterministic performance environments where consistent behavior from the
     first call matters more than faster startup.

Disabling tiered compilation (via DOTNET_TieredCompilation=0) forces the JIT to
produce fully optimized code on the first call, trading startup time for
immediate steady-state quality.


Question 4: How does dynamic PGO's devirtualization work? Why can it optimize
interface and virtual method calls? What are the limitations?
--------------------------------------------------------------------------------

Dynamic PGO's devirtualization works by observing which concrete types appear
most frequently at virtual or interface call sites during early (Tier 0 or
instrumented) execution. When the runtime recompiles a method at Tier 1 with
accumulated profile data, it can insert a type guard for the dominant type and
replace the virtual dispatch with a direct call.

For example, if an IAnimal.Speak() call site sees Dog 95% of the time, the JIT
may generate code equivalent to:

  if (obj is Dog d)
      d.Speak();       // direct call — can then be inlined
  else
      obj.Speak();     // fallback: standard virtual dispatch

This is called guarded devirtualization (GDV). The direct call can then be
inlined, which in turn enables constant propagation, dead branch elimination,
and other optimizations within the inlined body. The performance improvement
is often dramatic because it transforms an indirect call through a vtable into
a predictable direct call (or even eliminates the call entirely via inlining).

This works for both interface calls and virtual method calls because the
mechanism is the same: the runtime profiles which concrete types appear at
the call site, regardless of whether the static type is an interface or a
base class.

Limitations:

  1. Megamorphic call sites: if many different types appear with similar
     frequency, no single guard is effective and the fallback virtual dispatch
     dominates. GDV typically guards only one or two types.

  2. Warmup dependency: if the profiling period is too short, unrepresentative,
     or if the hot type has not yet appeared during instrumentation, the JIT may
     select the wrong type to guard or skip the optimization entirely.

  3. Workload shift: if the application's type distribution changes after Tier 1
     compilation (e.g., a different implementation becomes dominant), the guard
     will mostly fail, degrading to the slower fallback path plus the cost of
     the type check.

  4. Code size: each guarded call site adds a type check and two code paths
     (fast path + fallback), increasing the generated code footprint. For call
     sites that are not truly hot, this is wasted space.


Question 5: Why might code in a benchmark be optimized away by the JIT's dead
code elimination? How can you write benchmarks that survive this?
--------------------------------------------------------------------------------

The JIT compiler aggressively removes code whose results have no observable side
effects, a process known as dead code elimination (DCE). If a microbenchmark
computes a value but never returns it, writes it to a field, or passes it to
another un-inlinable method, the JIT may determine that the computation is
useless and delete the entire operation. The result is a benchmark that reports
near-zero execution time, completely misleading the developer.

This is particularly dangerous in hand-rolled benchmarks that look like:

  var sw = Stopwatch.StartNew();
  for (int i = 0; i < N; i++)
  {
      int result = ExpensiveComputation(i);
      // result is never used — JIT may remove the call entirely
  }
  sw.Stop();

To prevent this in frameworks like BenchmarkDotNet:

  1. Return the result: let the benchmark method return the computed value. BDN
     internally consumes this return value, forcing the JIT to keep the entire
     computation alive.

  2. Use Consume(): if returning is not possible (e.g., multiple outputs), pass
     the results to Consumer.Consume(), which is an opaque sink the JIT cannot
     see through.

  3. Assign to a volatile field: writing to a volatile field prevents the JIT
     from optimizing away the write, which anchors the computation.

  4. Use DoNotOptimize patterns: some benchmark frameworks provide explicit
     barriers that prevent DCE without adding measurement noise.

The core principle is that any benchmark must make its computed results visible
to the runtime in a way the JIT cannot prove is irrelevant.


Question 6: Explain the advantages and disadvantages of the CMOV instruction
compared to conditional branches. When does the JIT choose CMOV, and when does
it choose conditional branches?
--------------------------------------------------------------------------------

CMOV (Conditional Move) is a branchless instruction that evaluates a condition
and moves data only if the condition is true. Unlike a conditional branch (e.g.,
JE, JNE), CMOV does not alter the instruction pointer and therefore does not
interact with the branch predictor.

Advantages of CMOV:

  - Eliminates the risk of branch misprediction. On modern deeply-pipelined
    CPUs, a mispredicted branch incurs a severe penalty (typically 10-20 cycles
    to flush and refill the pipeline). CMOV converts control flow into a data
    dependency, avoiding this penalty entirely.
  - Produces more compact, straight-line code without the jump targets and
    alignment padding that branches require.
  - Performs consistently regardless of data patterns, which is valuable when
    the branch direction is genuinely unpredictable.

Disadvantages of CMOV:

  - CMOV forces the CPU to evaluate both sides of the condition before making
    the move, because it needs the values from both paths to be ready. This
    introduces a data dependency that the CPU cannot speculate past.
  - If the branch is highly predictable (e.g., 99% taken), a traditional
    conditional branch is actually faster because the CPU speculatively executes
    the likely path immediately and is almost never wrong.
  - CMOV cannot handle complex operations: if each branch path involves memory
    loads, function calls, or expensive computation, CMOV is not applicable
    because it only moves register values.

JIT strategy:

  The RyuJIT compiler uses heuristics and, when available, Dynamic PGO profile
  data to decide between CMOV and branches:

  - It prefers CMOV for unpredictable, short, and cheap operations such as
    Math.Min, Math.Max, simple ternary expressions (x > 0 ? a : b), and
    clamping operations.
  - It prefers traditional branches when the branch paths contain complex
    instructions, memory loads, or function calls, or when profile data shows
    the branch is heavily biased (the predictor will handle it efficiently).
  - The choice can also depend on the target CPU microarchitecture, as different
    processors have different CMOV latencies and pipeline depths.


Question 7: What are the differences between readonly struct and regular struct
in terms of JIT optimization? Why can calling non-readonly methods on an in
parameter cause defensive copies?
--------------------------------------------------------------------------------

Large structs are value types, so passing them by value usually means copying
their contents. If a struct is large and appears in hot code paths, those copies
can increase memory traffic, register pressure, and call overhead.

Different features address this in different ways:

  - ref passes the struct by reference, avoiding the copy, but allows mutation.
  - in also passes by reference but communicates read-only intent.
  - readonly struct tells the compiler and JIT that no instance member can
    mutate the value, eliminating ambiguity about side effects.

The critical difference: when the compiler encounters a non-readonly struct
passed via an in parameter, it must assume that any instance member access
(property getter, method call) could potentially mutate the struct's state. To
preserve the in contract (which promises the caller that its value will not
change), the compiler silently inserts a defensive copy of the entire struct
before each member access. For a 64-byte struct with 8 property accesses, this
means 8 hidden copies per call — often making the in version slower than plain
by-value passing.

With a readonly struct, the compiler knows that no instance member can mutate
state, so no defensive copies are needed. The in parameter works as intended:
a zero-copy read-only reference.

Note that in C# 8+, auto-implemented property getters (public int X { get; })
are implicitly readonly even on non-readonly structs. The defensive copy trap
specifically affects manually-implemented getters and methods that are not
marked readonly on non-readonly struct types.

The practical lesson is:

  - Always use readonly struct when a struct is logically immutable.
  - If you must use in with a non-readonly struct, mark individual getters as
    readonly to avoid defensive copies.
  - When in doubt, benchmark: defensive copies are invisible in source code but
    clearly visible in both disassembly and performance measurements.
