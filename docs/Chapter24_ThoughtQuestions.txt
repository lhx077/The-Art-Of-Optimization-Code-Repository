Question 1: When designing a library that must support Native AOT, what
principles help ensure AOT compatibility? If some features must use reflection,
how should the API be designed so consumers can still use the library in both
AOT and JIT environments?
--------------------------------------------------------------------------------

The core principle is to make runtime behavior explicit, analyzable, and
optional.

1. Avoid hidden runtime discovery.
   Native AOT works best when type usage is statically visible. Avoid designs
   that scan assemblies, walk arbitrary type graphs, or activate unknown types
   through reflection at runtime.

2. Prefer compile-time contracts over convention-based magic.
   Instead of saying “implement this interface and we will discover it later,”
   prefer APIs where the caller registers types explicitly, passes generated
   metadata, or uses source-generated glue code.

3. Separate the AOT-safe path from the dynamic path.
   If reflection is unavoidable, design two lanes:
   - an explicit AOT-friendly lane based on registration or generated metadata
   - a dynamic convenience lane for JIT environments

   The two lanes should be intentionally different in API shape rather than
   pretending they have identical runtime assumptions.

4. Annotate dynamic requirements precisely.
   If an API depends on constructors, public properties, or methods surviving
   trimming, use attributes such as DynamicallyAccessedMembers,
   RequiresUnreferencedCode, or RequiresDynamicCode so callers see the cost at
   compile time.

5. Keep reflection at the boundary, not in the core.
   The more of the library that depends on reflection, the harder it becomes to
   reason about trimming. Ideally, reflection is isolated to adapters while the
   main execution engine works on descriptors, delegates, or generated code.

6. Offer deterministic fallback points.
   AOT consumers should have a way to provide:
   - explicit type maps
   - generated serializers / binders
   - hand-written factories
   - descriptor objects

A practical API design is:
- Dynamic API for convenience:
  `RegisterFromAssembly(Assembly assembly)`
- AOT-safe API for production:
  `RegisterServices(IServiceCollection services, ServiceMap map)`
  or
  `RegisterGenerated(ServiceRegistry registry)`

That way, JIT users keep the ergonomic path, while AOT users opt into an
explicit path the compiler can fully understand.

So the rule is: design the static path as the first-class architecture, and
expose reflection only as an optional adapter with clear warnings and explicit
contracts.


Question 2: Compare the three regex modes: interpreted, Compiled, and Source
Generator. What are their compile-time and runtime characteristics? When should
each mode be chosen? Are there cases where Source Generator is worse than
Compiled?
--------------------------------------------------------------------------------

These three modes trade startup cost, throughput, and deployment constraints in
different ways.

1. Interpreted regex.
   - Compile-time cost: none beyond storing the pattern string in the assembly
   - Startup cost: low
   - Steady-state throughput: usually the lowest of the three
   - Memory/code size impact: modest

   Best when:
   - the regex runs rarely
   - startup simplicity matters more than peak throughput
   - the pattern is user-provided or highly dynamic

2. Compiled regex (`RegexOptions.Compiled`).
   - Compile-time cost: no extra build-time code generation
   - Startup/runtime preparation cost: higher, because IL or runtime structures
     are built for the pattern
   - Steady-state throughput: often better for hot regex workloads under JIT
   - Deployment impact: depends on runtime code generation support and is a poor
     fit for Native AOT expectations

   Best when:
   - the pattern is static
   - the regex is hot
   - the app runs long enough to amortize compilation overhead
   - the app is JIT-based, not AOT-focused

3. Source-generated regex (`[GeneratedRegex]`).
   - Compile-time cost: higher build work because the regex implementation is
     generated ahead of time
   - Startup cost: usually the best for static patterns because runtime
     compilation is avoided
   - Steady-state throughput: typically excellent and often comparable to or
     better than compiled regex
   - Deployment impact: strong fit for trimming and Native AOT because behavior
     is expressed as generated source

   Best when:
   - patterns are known at compile time
   - startup matters
   - AOT or trimming compatibility matters
   - you want performance without runtime regex compilation machinery

When to choose each mode:
- Interpreted: dynamic, rare, or low-importance regex use
- Compiled: JIT-only applications with a few very hot static expressions where
  startup cost is acceptable
- Source Generator: static patterns in modern production code, especially when
  startup, trimming, or AOT are important

Yes, there are cases where Source Generator can be worse than Compiled:
1. Extremely dynamic pattern sets.
   Source generation only helps when the pattern is known at build time.
2. Large numbers of rarely used static patterns.
   Generated code increases assembly size and build output even if many regexes
   are cold.
3. Workflows where build complexity matters more than startup.
   A huge generated regex surface can slightly increase build time and binary
   size with little runtime payoff.
4. JIT-only long-running services where startup is irrelevant and existing
   compiled regex throughput is already sufficient.

So Source Generator is usually the best default for static regex in modern .NET,
but not for dynamic patterns or for large cold pattern catalogs where generated
code size becomes wasteful.


Question 3: A Web API application using Entity Framework Core and dependency
injection wants to adopt Native AOT. What are the main challenges, and what
would a phased migration plan look like?
--------------------------------------------------------------------------------

The biggest challenge is not “publishing with a new flag.” It is removing all
runtime behaviors that assume dynamic code, reflection-based discovery, or broad
metadata availability.

Main challenges:

1. Dependency injection patterns.
   Reflection-heavy registration such as assembly scanning, open-ended service
   activation, or convention-based auto-registration may not trim or AOT well.

2. Configuration binding and options.
   Reflection-based binding paths may trigger trimming warnings unless the app
   switches to source-generated or statically analyzable binding patterns.

3. JSON serialization.
   Reflection-based serialization should be replaced with source-generated
   `System.Text.Json` metadata contexts.

4. EF Core model and query pipeline.
   EF Core has improved AOT support, but advanced features, provider behavior,
   migrations, proxies, and runtime model building can still create friction.
   Lazy-loading proxies are especially suspicious because they depend on dynamic
   behavior.

5. ASP.NET Core features that assume runtime discovery.
   MVC controller discovery, filters, model binding extensions, and third-party
   middleware may rely on reflection patterns that need review.

6. Third-party dependencies.
   A single package that performs runtime scanning or dynamic code generation can
   block the migration.

A phased migration plan:

Phase 1: Establish analyzer visibility.
- Turn on trimming analysis and AOT-related warnings.
- Publish with trimming first, before attempting full Native AOT.
- Treat warnings as architectural signals, not cosmetic noise.

Phase 2: Stabilize the outer edges.
- Replace reflection-based JSON serialization with generated contexts.
- Replace assembly-scanned DI registration with explicit registration or
  generated registration.
- Review configuration binding and move to analyzable patterns.

Phase 3: Simplify the web surface.
- Prefer Minimal APIs over highly dynamic MVC features when practical.
- Remove or isolate reflection-heavy filters, conventions, and plugin systems.
- Audit middleware and endpoint discovery.

Phase 4: Tame EF Core usage.
- Remove lazy-loading proxies.
- Prefer explicit projections and no-tracking read paths.
- Keep the DbContext model stable and avoid runtime-generated behaviors.
- Validate that the chosen provider and query features are supported in the AOT
  target shape.

Phase 5: Audit dependencies.
- For each package, answer:
  - does it scan assemblies?
  - does it emit dynamic code?
  - does it require broad metadata retention?
- Replace or isolate the problematic ones.

Phase 6: Produce a Native AOT slice.
- Start with a reduced deployment path such as a health API or a simple CRUD
  subset.
- Publish that slice with Native AOT.
- Measure startup, size, memory, and functional correctness.

Phase 7: Expand cautiously.
- Bring remaining endpoints and features over one group at a time.
- Keep a separate compatibility matrix for “works under JIT” versus “works under
  AOT publish.”

So the migration should start with trimming discipline, then remove dynamic
patterns at the boundaries, then progressively narrow and validate the runtime
surface until Native AOT becomes a natural consequence rather than a final leap.


Question 4: What advantages do incremental source generators have over
traditional ISourceGenerator? When implementing a complex source generator, how
should the data pipeline be designed to maximize incremental efficiency?
--------------------------------------------------------------------------------

Incremental generators are better because they model generation as a cached data
pipeline instead of a monolithic “recompute everything” step.

Advantages over traditional `ISourceGenerator`:

1. Incremental recomputation.
   If only one input file changes, only the affected portion of the pipeline is
   recomputed.

2. Better IDE responsiveness.
   Editors do not need to rerun the whole generator for every small edit.

3. Deterministic separation of stages.
   Syntax discovery, semantic analysis, normalization, and code emission can be
   modeled as explicit transforms.

4. Easier reasoning about performance.
   Because the pipeline is composed of nodes, it is easier to see where expensive
   work happens and where equality/caching boundaries should exist.

5. Better scalability.
   Large solutions benefit much more because repeated work is avoided.

To maximize efficiency in a complex generator, design the pipeline around stable,
small, equatable data.

Good pipeline principles:

1. Filter early with syntax.
   Use syntax predicates to discard irrelevant nodes before semantic analysis.
   Semantic model access is expensive, so the syntax stage should be as narrow as
   possible.

2. Project to compact intermediate records.
   After semantic analysis, convert symbols into small immutable value objects
   that contain only what generation needs.

3. Normalize aggressively.
   Do not carry the full Roslyn symbol graph through later stages if a simple
   descriptor like:
   - namespace
   - type name
   - accessibility
   - property list
   is enough.

4. Preserve stable equality.
   Intermediate types should implement meaningful value equality so Roslyn can
   tell when nothing important changed.

5. Split independent branches.
   If one part of the generator creates registration metadata and another emits
   diagnostics, model them as separate flows so each can cache independently.

6. Avoid global aggregation too early.
   Combining all inputs into one giant list too soon causes tiny edits to
   invalidate too much downstream work.

7. Emit per-target where possible.
   Generating one file per discovered type is often more incremental than
   generating one huge monolithic file for the whole compilation.

8. Join compilation-wide inputs only at the end.
   Things like `AnalyzerConfigOptionsProvider` or referenced assemblies should be
   combined with discovered type data only where necessary.

A healthy mental model is:
- syntax filter
- semantic bind
- normalize to small descriptors
- group only when required
- emit minimally scoped outputs

So the key advantage of incremental generators is not just “faster generation.”
It is the ability to encode the generator as a cache-friendly dependency graph
where small edits stay small.


Question 5: Discuss the relationship between trimming and security. Trimming can
remove unnecessary code and reduce attack surface, but trimming mistakes can also
cause runtime failure. How should teams balance security and functional
completeness?
--------------------------------------------------------------------------------

Trimming improves security only when it is treated as a controlled engineering
process, not as a blind size-reduction switch.

Security benefits of trimming:
1. Smaller attack surface.
   Unused endpoints, parsers, codecs, and helper paths may disappear from the
   shipped binary.
2. Less dormant code.
   Code that never ships cannot be exploited in production.
3. Better dependency awareness.
   Trimming analysis often forces teams to discover which dynamic features and
   libraries they really depend on.

Risks of trimming:
1. Runtime failure from missing metadata or members.
   Reflection, serializers, binders, and plugin systems may fail only under
   specific production paths.
2. False confidence.
   A smaller binary is not automatically a safer binary if important validation,
   auditing, or error paths were accidentally broken.
3. Hard-to-detect breakage.
   Trimming issues may not appear in unit tests if test coverage does not execute
   the affected dynamic path.

A balanced strategy is:

1. Make warnings actionable.
   Do not suppress trimming warnings casually. Each warning should be classified:
   - safe and understood
   - requires annotation
   - requires architectural redesign

2. Prefer explicit preservation to blanket preservation.
   Preserve only the members actually required by reflection or serialization.
   Broad keep-everything descriptors reduce the value of trimming.

3. Test the published artifact, not just the Debug build.
   Run integration tests against the trimmed publish output because that is where
   failures actually occur.

4. Protect security-critical behavior first.
   Authentication, authorization, validation, audit logging, and cryptographic
   flows must be verified explicitly after trimming.

5. Use staged rollout.
   Start with non-critical services or a reduced feature slice before trimming
   every production workload.

6. Keep architecture aligned with analyzability.
   The safest trimmed systems are usually the ones that rely on explicit
   registration, generated metadata, and narrow dynamic seams.

So the right balance is: use trimming to remove genuinely unnecessary code, but
never trade away correctness for binary size. Security improves when trimming is
verified, scoped, and test-backed — not when teams simply aim for the smallest
possible executable.


Question 6: Compare the pros and cons of JIT compilation and AOT compilation
(such as Native AOT). In what scenarios does JIT have an advantage, and in what
scenarios is AOT more suitable?
--------------------------------------------------------------------------------

Native AOT can outperform JIT in scenarios where startup, deployment simplicity,
and predictable early execution matter most. Because native code is produced
before execution, the program avoids most runtime compilation overhead. This can
reduce startup latency, improve cold-start behavior, and lower the amount of work
needed during process initialization.

That is especially valuable for:

  - CLI tools that must respond immediately
  - short-lived processes like serverless functions
  - cold-start-sensitive workloads where first-request latency matters
  - restricted environments where JIT compilation is undesirable or forbidden

AOT also produces self-contained binaries that do not require the .NET runtime
to be installed on the target machine, simplifying deployment.

However, JIT can still win in other situations because it sees information that
AOT often cannot know in advance. For example, the JIT can tailor code to the
exact CPU running the process and combine tiered compilation with dynamic PGO.

Potential JIT advantages include:

  - CPU-specific specialization at execution time (e.g., using AVX-512 if
    available, falling back to SSE2 otherwise)
  - optimization decisions based on real observed hot paths via dynamic PGO
  - adaptive devirtualization and inlining influenced by live profiles
  - full support for runtime features like reflection, dynamic code generation,
    and unrestricted generic instantiation

AOT limitations include:

  - limited or no support for reflection-heavy patterns
  - no runtime profile-guided optimization
  - code must be specialized for a particular CPU target at build time
  - larger binary sizes when all possible code paths must be compiled ahead

So Native AOT tends to favor predictability and startup, while JIT tends to favor
runtime adaptability and, in long-running workloads, better eventual steady-state
optimization. Neither is universally superior. They optimize different parts of
the performance envelope, and the right choice depends on the workload profile.
