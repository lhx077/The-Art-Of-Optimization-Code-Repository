Question 1: Consider the following struct definition. What is its size under the
default sequential layout? If you reorder the fields, what is the smallest size
that can be achieved?

struct MixedFields
{
    public byte A;
    public double B;
    public short C;
    public int D;
    public byte E;
    public long F;
}
--------------------------------------------------------------------------------

Under the default sequential layout, field order is preserved and the runtime
inserts padding so each field begins at an address suitable for its natural
alignment.

A likely layout is:
  - A at offset 0, size 1
  - padding 7 bytes so B can start at offset 8
  - B at offset 8, size 8
  - C at offset 16, size 2
  - padding 2 bytes so D can start at offset 20
  - D at offset 20, size 4
  - E at offset 24, size 1
  - padding 7 bytes so F can start at offset 32
  - F at offset 32, size 8

The total becomes 40 bytes.

The waste comes from placing small fields before large ones. If the fields are
reordered from largest to smallest, padding can be reduced substantially.

For example:
  - double B at offset 0
  - long F at offset 8
  - int D at offset 16
  - short C at offset 20
  - byte A at offset 22
  - byte E at offset 23

Now the data occupies 24 bytes, which is already aligned to the largest field
requirement. So the struct can be reduced from 40 bytes to 24 bytes.

This example shows why field order matters: the raw sum of field sizes is only 24
bytes, but poor ordering can inflate the actual layout to 40 bytes.


Question 2: In a high-performance particle system, each particle has position
(3 floats), velocity (3 floats), color (4 bytes), lifetime (1 float), and size
(1 float). If the system must update the position and velocity of one million
particles every frame, would you choose AoS or SoA? Explain why and give a
concrete data structure design.
--------------------------------------------------------------------------------

For this workload, SoA is the better choice.

The critical observation is that the hot update loop touches only a subset of the
particle state: positions and velocities. Color may not be needed during physics
updates, and lifetime or size may be used less frequently. In an AoS layout,
each particle record stores all fields together, so every iteration pulls extra
bytes into cache even when they are irrelevant to the current computation.

With one million particles, that wasted traffic becomes expensive.

SoA improves locality because each property lives in its own dense array. The
update loop can stream through the position and velocity arrays directly, which:
  - reduces cache pollution from rarely used fields
  - makes prefetching more effective
  - maps naturally to SIMD because adjacent values of the same type are packed
    together

A practical design is:
  - float[] PositionX, PositionY, PositionZ
  - float[] VelocityX, VelocityY, VelocityZ
  - float[] Lifetime
  - float[] Size
  - uint[] Color or byte[] arrays for RGBA channels

Then a movement update can operate only on the six float arrays for position and
velocity. Rendering or color updates can access the color storage separately.

AoS would still be reasonable if particles were always processed as whole records
in nearly every system, but that is not the case here. The dominant work is
component-wise numeric updates, so SoA matches the access pattern better and is
more likely to saturate cache bandwidth and SIMD throughput.


Question 3: Suppose you are building a multi-threaded counter where four threads
maintain their own counts and later sum them. If you simply use a struct with
four long fields, what performance issue can arise? How can memory layout fix it?
Provide concrete code.
--------------------------------------------------------------------------------

The main problem is false sharing.

If four long fields are placed next to each other, they are likely to live on the
same cache line. Even though each thread updates a different field, the CPU cache
coherence system tracks ownership at cache-line granularity, not at field
granularity. So every write by one thread can invalidate the cache line held by
another thread. The result is unnecessary cache traffic and much lower
throughput.

The fix is to separate each thread-local counter onto its own cache line by
adding explicit padding or using a struct size that matches the cache-line width.
A common assumption is 64-byte cache lines.

One approach is:

```csharp
using System.Runtime.InteropServices;
using System.Threading;

[StructLayout(LayoutKind.Explicit, Size = 64)]
public struct PaddedCounter
{
    [FieldOffset(0)]
    public long Value;
}

public sealed class CounterSet
{
    private readonly PaddedCounter[] _counters = new PaddedCounter[4];

    public void Increment(int workerIndex)
    {
        _counters[workerIndex].Value++;
    }

    public long Total()
    {
        long sum = 0;
        for (int i = 0; i < _counters.Length; i++)
        {
            sum += Volatile.Read(ref _counters[i].Value);
        }

        return sum;
    }
}
```

Now each logical counter occupies an entire cache line, so writes from different
threads do not constantly invalidate one another.

The broader lesson is that thread ownership alone is not enough. Physical memory
placement also matters when many cores write at high frequency.


Question 4: Unions implemented with FieldOffset(0) have an important limitation
in .NET: reference-type fields cannot overlap with value-type fields. Explain why
this restriction exists and what could go wrong if such overlap were allowed.
--------------------------------------------------------------------------------

This restriction exists because the garbage collector must know exactly which
memory locations contain managed object references.

A reference field is not just ordinary bits. The runtime treats it as a pointer
into the managed heap, tracks it during collection, updates it if the object is
moved, and uses it to keep the referenced object alive. A value-type field, by
contrast, is treated as raw data with no GC meaning.

If the same memory were allowed to act as both a reference and a non-reference
value, the runtime would lose a coherent interpretation of that storage.

Possible failures include:
  - The GC may treat arbitrary data bits as an object reference.
  - A real reference might be overwritten by raw bytes, causing the runtime to
    miss a live object.
  - The GC could follow a bogus pointer into invalid memory.
  - Object relocation could update memory that the program expects to be plain
    value data.
  - Type safety and heap integrity could be broken, potentially leading to memory
    corruption or runtime crashes.

So the restriction is fundamentally about maintaining a trustworthy GC map. The
runtime needs a stable answer to the question: which slots are references? An
overlapping union of reference and non-reference data would make that answer
ambiguous, and the GC cannot safely operate under ambiguity.


Question 5: In data-oriented design, we discuss the handle pattern as an
alternative to direct object references. What are its advantages and disadvantages?
When should it be preferred?
--------------------------------------------------------------------------------

A handle pattern replaces direct object references with lightweight identifiers,
often an index plus a generation counter. The identifier is resolved through a
central storage structure that owns the actual data.

Advantages:
  1. Better data locality.
     Objects or components can be stored densely in arrays instead of scattered
     across the heap.

  2. Easier relocation and compaction.
     Data can move inside internal storage without invalidating external handles,
     as long as the mapping table is updated.

  3. Safer lifetime checks.
     Generation counters help detect stale handles and prevent use-after-free-
     style bugs at the application level.

  4. Better fit for ECS and DOD systems.
     Systems can process dense spans of homogeneous data instead of chasing many
     object references.

  5. More control over ownership.
     The storage layer, not arbitrary callers, decides how memory is organized
     and recycled.

Disadvantages:
  1. Extra indirection.
     Accessing an entity requires resolving the handle through a table.

  2. More bookkeeping.
     You must manage slot reuse, generation increments, free lists, and validity
     checks.

  3. Less ergonomic API design.
     Direct object references are simpler and more natural in ordinary OO code.

  4. Harder debugging in some cases.
     A handle value is less descriptive than an object graph unless tooling is
     built around it.

The handle pattern should be preferred when:
  - the system manages very large numbers of entities or components
  - data locality matters more than object identity semantics
  - objects are created, destroyed, and recycled frequently
  - stale reference protection is valuable
  - processing is organized as bulk operations over dense component arrays

It is less attractive for small application domains where ordinary object
references are already clear, safe, and fast enough. In short, handles trade
simplicity for control, locality, and scalability.
