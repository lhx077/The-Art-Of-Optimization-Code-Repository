Question 1: XOR has an important property: a ^ b ^ b = a. What are some real
programming applications of this property? Give at least two examples and explain
the principle.
--------------------------------------------------------------------------------

The identity a ^ b ^ b = a follows from two facts: XOR is associative and
commutative, and any value XORed with itself becomes zero. In other words,
(a ^ b) ^ b = a ^ (b ^ b) = a ^ 0 = a.

This makes XOR useful whenever a transformation should be reversible without
extra state.

Example 1: Finding a value that appears an odd number of times.
If every repeated value appears an even number of times, all of those pairs
cancel each other out under XOR. The final result is therefore the value whose
total count is odd. This works because order does not matter and equal values
eliminate one another.

Example 2: Toggling flags.
A bit mask can be XORed into a flag word to flip selected bits. Applying the
same mask a second time restores the original state. That makes XOR a natural
tool for reversible state changes such as toggling permissions, options, or
parity bits.

Example 3: Lightweight stream-style encoding.
If data is XORed with a key, the same key can be XORed again to recover the
original bytes. The principle is exactly the same cancellation rule. This is
not strong cryptography by itself, but it demonstrates why XOR is central in
many encoding and cryptographic constructions.

Example 4: Swapping two variables without a temporary.
The classical XOR-swap sequence uses repeated cancellation to reconstruct the
original values in the opposite locations. Although modern code usually prefers
a temporary variable for readability and optimization quality, the example still
illustrates the algebraic reversibility of XOR.

The common theme is that XOR is excellent for symmetric transformations: apply
once to mix in information, apply again with the same operand to remove it.


Question 2: Suppose you need to find the only element that appears an odd number
of times in an array, while every other element appears an even number of times.
How can XOR solve this in O(n) time and O(1) space? What if two elements appear
an odd number of times?
--------------------------------------------------------------------------------

For the single odd-occurring element case, initialize an accumulator to zero and
XOR every array element into it.

If all but one value appear an even number of times, each repeated value cancels
out. The accumulator is left holding exactly the odd-occurring value.

Why it works:
  - x ^ x = 0
  - 0 ^ x = x
  - XOR can be regrouped in any order

So the algorithm is:
  1. result = 0
  2. for each value v in the array: result ^= v
  3. return result

This is O(n) time and O(1) extra space.

If two different values appear an odd number of times, XORing the whole array
produces a ^ b, where a and b are the two target values. That combined result is
not enough by itself to identify each one, but it does reveal at least one bit
where they differ.

The usual strategy is:
  1. XOR the whole array to get combined = a ^ b.
  2. Isolate one set bit from combined, for example the lowest set bit.
  3. Partition the array into two groups based on whether that bit is set.
  4. XOR each group separately.

Because a and b differ on that bit, they go into different groups. All even-
occurring distractor values still cancel inside their own groups. One group
produces a, the other produces b.

So the two-odd-elements version still runs in O(n) time and O(1) extra space,
but it uses one extra partitioning idea derived from the XOR difference mask.


Question 3: BitOperations.PopCount is very useful for computing Hamming distance.
Analyze several software implementations of PopCount that do not use hardware
instructions, and compare their efficiency.
--------------------------------------------------------------------------------

Software PopCount implementations vary mainly in how much work they do per set
bit or per machine word.

Method 1: Naive shift-and-test loop.
Repeatedly test the low bit, add it to a counter, then shift the value right by
one bit until the value becomes zero.

This is simple and portable, but it may require up to one iteration per bit of
the input type. For a 64-bit value, the worst case is 64 loop iterations.
Branches and loop-carried dependencies also make it relatively slow.

Method 2: Kernighan's algorithm.
Use x &= x - 1 in a loop. Each iteration clears the lowest set bit, and the
number of iterations equals the number of one bits.

This is often much better for sparse values because it does work proportional to
the population count rather than the bit width. However, for dense values it can
still require many iterations, and the loop remains branchy.

Method 3: Table lookup.
Precompute the popcount for all byte values 0..255, then sum the counts of the
individual bytes in the input word.

This turns the problem into a few table accesses and additions. It is usually
more stable than loop-per-bit methods, but it introduces memory reads and may be
limited by cache behavior or indexing overhead.

Method 4: SWAR / parallel bit counting.
Use masks and shifts to sum bit counts inside progressively larger bit fields,
such as 2-bit groups, then 4-bit groups, then bytes, and so on.

A classic sequence uses constants such as:
  - 0x5555...
  - 0x3333...
  - 0x0F0F...

This approach performs a fixed number of arithmetic and bitwise operations with
no data-dependent loop count. It is typically the fastest pure-software scalar
method on general-purpose CPUs when no dedicated popcount instruction is used.

Efficiency comparison:
  - Naive shift-and-test: simplest, usually slowest.
  - Kernighan: excellent for sparse bit patterns, variable cost.
  - Table lookup: decent and predictable, but relies on memory access.
  - SWAR: fixed-cost, branchless, usually the best general scalar software
    implementation.

So if hardware PopCount is unavailable, SWAR is usually the strongest default,
while Kernighan remains attractive when inputs are known to be very sparse.


Question 4: A branchless maximum function based on a - b can fail when the
subtraction overflows. Design a branchless maximum function that correctly
handles all int values and explain the method.
--------------------------------------------------------------------------------

The overflow problem appears because the sign of a - b is not reliable when the
subtraction wraps around. A correct branchless strategy must decide whether the
inputs have different signs before trusting the subtraction result.

A safe approach is to split the logic into two cases:
  1. If a and b have different signs, the non-negative one is larger.
  2. If they have the same sign, the sign of a - b is safe to use.

This can be expressed with bit operations only.

Let:
  - signA be the sign bit of a
  - signB be the sign bit of b
  - signDiff indicate whether the signs differ
  - diffSign be the sign bit of a - b

When signDiff is 1, choose based on signA.
When signDiff is 0, choose based on diffSign.

Then build a selector bit that is 1 when b is larger and 0 when a is larger, and
blend the values with bit masks instead of branches.

The core idea is not the exact syntax but the decision structure: avoid using the
subtraction sign when overflow is possible, and only use it when the operands
share the same sign. That preserves correctness for int.MinValue, int.MaxValue,
and every mixed-sign combination.

This design is still branchless in the sense that it uses arithmetic and masking
instead of control-flow branches, but it is also overflow-safe because it does
not derive ordering from an invalid subtraction case.


Question 5: Bitmaps may waste a lot of space when representing sparse sets.
Discuss the basic idea of compressed bitmaps such as Roaring Bitmap and how they
balance space efficiency with operation efficiency.
--------------------------------------------------------------------------------

A plain bitmap is excellent when the universe of possible values is dense,
because membership tests and set algebra are fast and simple. The problem is that
it allocates space for every possible position, even if only a tiny fraction of
those positions are actually present.

Compressed bitmap formats such as Roaring Bitmap solve this by dividing the value
space into chunks and choosing different internal representations depending on
local density.

The basic Roaring idea is:
  1. Split integers by their high bits into containers.
  2. Within each container, store the low bits using the representation that best
     fits that chunk.

Typical container choices include:
  - array containers for very sparse chunks
  - bitmap containers for dense chunks
  - run containers for long consecutive ranges

This hybrid design gives a strong balance.

Space efficiency:
  - Sparse regions do not pay the full dense-bitmap cost.
  - Dense regions still use a bitmap where it is compact enough and very fast.
  - Long runs can be compressed more effectively than listing each value.

Operation efficiency:
  - Containers are organized by chunk key, so lookup and set operations work on
    relatively small local structures.
  - Set algebra such as AND, OR, and XOR can dispatch to specialized routines
    based on the pair of container types being combined.
  - Dense chunks still benefit from word-level or SIMD-style bulk bit operations.

The important tradeoff is that compressed bitmaps are more complex than plain
bitmaps, but they avoid paying a worst-case space cost everywhere. Roaring works
well because it does not insist on one universal representation. Instead, it
adapts per chunk, which preserves much of the speed of bitmaps while recovering a
large amount of wasted space in sparse datasets.
