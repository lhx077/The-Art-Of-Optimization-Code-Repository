Question 1: Consider the following code snippet. Analyze the possible concurrency
issues and propose improvements.

public class Counter
{
    private int _count;
    private readonly object _lock = new object();

    public int Count => _count;

    public void Increment()
    {
        lock (_lock)
        {
            _count++;
        }
    }

    public void IncrementIfLessThan(int max)
    {
        if (_count < max)
        {
            lock (_lock)
            {
                _count++;
            }
        }
    }
}
--------------------------------------------------------------------------------

The main bug is a check-then-act race.

Increment uses a lock correctly, so individual increments are serialized.
However, IncrementIfLessThan reads _count outside the lock, then decides whether
an increment is allowed, and only later enters the critical section. Between the
outer read and the locked increment, another thread may already have increased the
counter. As a result, multiple threads can all observe _count < max and each add
one, so the final count can exceed the limit.

There is also a visibility concern. The Count property returns _count without any
synchronization. On modern .NET runtimes, aligned int reads are atomic, but atomic
is not the same as synchronized. A thread may observe a stale value if no memory
ordering is enforced.

A simple fix is to move the full condition check under the same lock:

```csharp
public int Count
{
    get
    {
        lock (_lock)
        {
            return _count;
        }
    }
}

public void IncrementIfLessThan(int max)
{
    lock (_lock)
    {
        if (_count < max)
        {
            _count++;
        }
    }
}
```

This is correct and easy to reason about. The downside is that every read now
acquires the lock.

If the counter is very hot and only simple integer operations are needed, an
Interlocked-based design may scale better. For example, Increment can use
Interlocked.Increment, and IncrementIfLessThan can be implemented with a CAS loop
that retries until it either succeeds or observes that the limit has already been
reached.

So the key rule is: when correctness depends on both the condition and the state
update, they must be protected by the same synchronization mechanism.


Question 2: In what situations can SpinLock outperform Monitor (the lock
statement)? In what situations can it perform worse? Analyze this from CPU usage,
context-switch overhead, and critical-section length.
--------------------------------------------------------------------------------

SpinLock can outperform Monitor when the wait time is extremely short and lock
contention is brief.

Why it can be faster:
  - A thread that spins stays in user mode and repeatedly checks whether the lock
    has become free.
  - If the current owner is about to leave the critical section very soon,
    spinning avoids a kernel-assisted park/unpark cycle.
  - That means no context switch, no scheduler handoff, and no cold wake-up path.

Typical cases where SpinLock may win:
  - the critical section is only a few instructions long
  - contention exists, but only for very short bursts
  - the protected state is touched at extremely high frequency
  - the waiting thread is expected to run on another core immediately

Why it can be worse:
  - While spinning, the waiting thread burns CPU cycles continuously.
  - If the lock holder is delayed, preempted, or blocked, all spinners waste CPU
    doing no useful work.
  - Under long critical sections, the wasted cycles can be much more expensive
    than a single context switch.
  - On oversubscribed systems, spinning can even delay the thread that currently
    holds the lock, making the contention worse.

Cases where SpinLock usually performs worse:
  - the critical section may run for microseconds or longer
  - the lock protects I/O, blocking calls, allocation-heavy work, or async-incompatible code
  - the machine has fewer available cores than runnable threads
  - fairness and debuggability matter more than raw microbenchmark speed

Monitor is generally the safer default because it adapts better to real workloads.
A thread can block instead of wasting a core, and the programming model is much
simpler. SpinLock is a specialized tool for very short, carefully bounded critical
sections in performance-sensitive code where measurements prove it helps.


Question 3: The factory delegate passed to ConcurrentDictionary<TKey, TValue>
GetOrAdd may be invoked multiple times. Is this a design flaw or an intentional
tradeoff? If you must ensure the factory runs only once, what solutions are
available? What are their tradeoffs?
--------------------------------------------------------------------------------

This behavior is intentional.

ConcurrentDictionary is designed to keep the common fast path highly concurrent.
If GetOrAdd held an exclusive lock while executing the factory, every competing
thread would have to wait for arbitrary user code. That would greatly reduce
throughput and would also introduce risks such as lock convoying, reentrancy
problems, and accidental deadlocks.

Instead, the dictionary may allow multiple threads to compute the value in
parallel, then only one result wins the race and gets stored. The others are
thrown away. So the factory must be treated as speculative work.

This is not a design flaw. It is an explicit tradeoff: higher concurrency in
exchange for allowing duplicate factory execution.

If single execution is required, common solutions include:

1. Store Lazy<T> inside the dictionary.
   Example idea:
   ```csharp
   var lazy = dictionary.GetOrAdd(key, _ => new Lazy<T>(factory));
   return lazy.Value;
   ```
   Pros:
     - simple and common
     - Lazy<T> can guarantee one-time execution of the wrapped factory
   Cons:
     - multiple Lazy<T> wrappers may still be allocated during races
     - exception caching semantics of Lazy<T> may or may not match requirements

2. Store Task<T> or AsyncLazy-style wrappers.
   Pros:
     - works naturally for async initialization
     - callers can await the same in-flight work
   Cons:
     - more complex lifecycle and exception handling
     - cancellation semantics must be designed carefully

3. Use an outer per-key lock.
   Pros:
     - exact single execution semantics
     - full control over initialization policy
   Cons:
     - added locking complexity
     - lock objects themselves need management
     - can reduce concurrency for hot keys

4. Use ImmutableDictionary with copy-on-write updates guarded by a lock.
   Pros:
     - clear semantics for read-mostly caches
   Cons:
     - usually slower for highly contended write paths
     - not ideal if many keys are initialized concurrently

So the current GetOrAdd design is deliberate. If one-time initialization matters
more than maximum throughput, the usual answer is not to fight the dictionary API
directly, but to place a one-time-initialization wrapper such as Lazy<T> around
the expensive value.


Question 4: Consider a high-frequency trading system that maintains an order book.
It must support add order, cancel order, match order, and query best price.
Analyze which data structures and synchronization strategy would provide the best
performance.
--------------------------------------------------------------------------------

A high-performance order book usually benefits from separating hot-path matching
state from secondary lookup structures.

The core operations have different needs:
  - Add order: insert by price level and append to time priority within that level.
  - Cancel order: locate a specific order quickly.
  - Match order: access the best bid or best ask repeatedly with minimal overhead.
  - Query best price: return top-of-book immediately.

A practical design is:
  1. Two sides of book: bids and asks.
  2. For each side, maintain price levels in a sorted structure.
     - bids sorted descending
     - asks sorted ascending
  3. Within each price level, maintain a FIFO queue or doubly linked list of
     resting orders to preserve price-time priority.
  4. Maintain a hash map from OrderId to the order node so cancellation is O(1)
     after lookup.

Suitable structures:
  - price tree or skip list for ordered levels
  - doubly linked list per level for FIFO matching and O(1) removal when a node is known
  - dictionary from OrderId to node/level metadata for fast cancel

For synchronization, the best strategy depends on whether matching is single-core
serialized or multi-core parallel.

In many real trading systems, the matching engine itself is intentionally
single-writer. All mutations for one instrument are funneled through one dedicated
thread or one partition owner. That eliminates internal lock contention on the
hottest path and preserves deterministic ordering. Readers can then observe
snapshots published atomically, for example through immutable top-of-book state or
copy-on-write snapshots for external consumers.

This single-writer design is often better than fine-grained locking because:
  - matching logic is inherently order-sensitive
  - cancel and match frequently touch the same structures
  - lock contention on best-price levels would be severe under burst traffic
  - deterministic sequencing is important in trading systems

If multiple instruments are present, partition by symbol so each partition has its
own single writer. That scales horizontally without forcing a single global lock.

For read access, publish a compact immutable snapshot of the best bid/ask using
Volatile.Write or Interlocked.Exchange. Then query-best-price becomes essentially
lock-free for consumers.

So the best-performance answer is typically:
  - ordered price-level structure plus FIFO queues and an OrderId index
  - single-writer partitioned mutation model
  - lock-free or snapshot-based read publication for market-data queries


Question 5: Channel<T> and BlockingCollection<T> can both implement the
producer-consumer pattern. Compare their suitability in these scenarios:
  - producers and consumers are both synchronous
  - producers are synchronous, consumers are asynchronous
  - multiple consumers compete for work
  - backpressure is required
--------------------------------------------------------------------------------

BlockingCollection<T> is the older synchronous-first abstraction. It is built
around blocking waits and integrates naturally with thread-based producer-consumer
code.

Channel<T> is the newer abstraction designed for both high-throughput and async
pipelines. It supports non-blocking async waits, bounded modes, and richer
configuration for single-reader or single-writer optimization.

Scenario 1: both producers and consumers are synchronous.
  - BlockingCollection<T> is perfectly reasonable here and often simpler.
  - Channel<T> can still work, especially with TryWrite and TryRead, but its main
    strength is not required in a purely synchronous design.

Scenario 2: producers are synchronous, consumers are asynchronous.
  - Channel<T> is clearly better.
  - The producer can call TryWrite or WriteAsync if needed, and the consumer can
    await ReadAsync or ReadAllAsync without tying up worker threads.
  - BlockingCollection<T> does not fit async consumption well because blocking a
    thread is not the same as awaiting work.

Scenario 3: multiple consumers compete for work.
  - Both can support this pattern.
  - BlockingCollection<T> allows multiple threads to call Take.
  - Channel<T> allows multiple readers to await data concurrently.
  - Channel<T> usually integrates better with modern async services, while
    BlockingCollection<T> remains acceptable for classic thread-pool worker code.

Scenario 4: backpressure is required.
  - Channel<T> is generally better because bounded channels expose explicit full
    modes such as Wait, DropOldest, DropNewest, or DropWrite.
  - BlockingCollection<T> can be bounded too, but the model is centered on
    blocking threads rather than shaping asynchronous flow cleanly.

In summary:
  - synchronous-only pipeline: BlockingCollection<T> is still a valid simple choice
  - any async consumer path: prefer Channel<T>
  - modern multi-stage pipelines: Channel<T> is usually the better long-term choice
  - explicit backpressure policy: Channel<T> offers more control


Question 6: The following code attempts to implement thread-safe lazy
initialization. Analyze its correctness and performance characteristics.

public class LazyInit<T> where T : class, new()
{
    private T _value;
    private volatile bool _initialized;
    private readonly object _lock = new object();

    public T Value
    {
        get
        {
            if (!_initialized)
            {
                lock (_lock)
                {
                    if (!_initialized)
                    {
                        _value = new T();
                        _initialized = true;
                    }
                }
            }
            return _value;
        }
    }
}
--------------------------------------------------------------------------------

This is a double-checked locking pattern.

In modern .NET, this version is basically correct because the volatile write to
_initialized publishes the constructed reference only after _value has been
assigned. A thread that later observes _initialized == true through a volatile
read will also observe the preceding write to _value.

So the code is intended to provide:
  - one-time initialization
  - lock avoidance on the fast path after initialization

That said, several caveats remain.

1. The generic constraint requires a public parameterless constructor.
   This makes the utility less flexible than Lazy<T>, which can accept arbitrary
   factory logic.

2. Exception behavior is different from Lazy<T>.
   If new T() throws, initialization simply remains incomplete and another caller
   will retry later. That may or may not be desirable.

3. The correctness argument is subtle.
   Double-checked locking is easy to get wrong, and many teams prefer the standard
   library implementation because it is clearer and already heavily tested.

4. The fast path is cheap but not free.
   Each read still performs a volatile read of _initialized. That is usually much
   cheaper than taking a lock, but it is still a memory-ordering operation.

In terms of performance:
  - first access pays for locking and construction
  - later accesses avoid the lock and only perform the outer check plus a field return
  - under heavy contention during first initialization, only one thread constructs
    the object and the others wait on the lock

In production code, Lazy<T> is usually the preferred abstraction because it has
well-defined execution modes, clearer semantics, and fewer opportunities for
subtle bugs. This custom implementation is educational and can be correct, but it
is harder to justify unless you have a very specific reason to avoid the built-in
helper.
